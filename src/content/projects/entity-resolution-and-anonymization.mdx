Picture a company's Slack, email and issue tracker. One engineer shows up as "Jordan", as "J. Lee", as a
work address and as a handle, often in the same thread. Before data like that can be used to train an AI
model, every real person in it has to disappear, and the conversation still has to make sense.

That is the job of the anonymization pipeline on Mercor's Data Acquisition team. It is team work. My part is
the step that decides who is who, with the evals that measure it, and the step that picks what each
person becomes.

## Why find and replace is not enough

Company data is not one kind of file. The same person turns up in email headers, chat exports,
spreadsheets, PDFs, slide decks and screenshots. Whatever fake they get has to agree across all of them,
or the data starts to contradict itself.

Nobody reads this much text by hand. Whatever rule the pipeline follows for one name, it follows
everywhere at once, mistakes included.

## Three obvious answers, and how each one breaks

<figure class="os-figure">

```text
 the thread
   Jordan:   is the build red?
   Sam:      yes, J. Lee broke it
   J. Lee:   fixed now

 black out every name
   ####:     is the build red?
   ####:     yes, #### broke it
   ####:     fixed now        (who fixed it?)

 a new random fake for every mention
   Ravi:     is the build red?
   Mei:      yes, Omar broke it
   Lena:     fixed now        (one person is now three)

 one fake identity per person
   Ravi:     is the build red?
   Mei:      yes, R. Iyer broke it
   R. Iyer:  fixed now
```

<figcaption>One made-up thread under three treatments. Only the last keeps the conversation intact, and it needs to know that Jordan and J. Lee are the same person.</figcaption>
</figure>

**Black out the names.** The thread survives as text and dies as a conversation: nobody can tell any
more who said what to whom.

**Give every mention a random fake.** Now the conversation has people in it, but the wrong number of
them. "Jordan" in one message and "J. Lee" in the next become strangers.

**Link mentions by comparing everything.** The fix is to find every mention of a person, link them, and
give that person one fake identity everywhere. Comparing every mention with every other one grows with
the square of the count, so it stops fitting long before a company's data runs out. And linking has a
trap: if A is B and B is C, then A is C, so one bad link can weld two whole groups of people into one.

## How the pipeline works

Each step answers one question and hands a table to the next.

<figure class="os-figure">

```text
 read       what is the text, and where exactly
   |        did each piece come from?
   v
 detect     which spans are personal data,
   |        and of what kind?
   v
 resolve    which of those spans are the same person?
   |
   v
 choose     what does each mention become?
   |
   v
 rewrite    put each fake back in the exact spot
            it came from
```

<figcaption>The pipeline's steps, in order. Every kind of file goes through the same steps, so a person gets one answer across all of them.</figcaption>
</figure>

**Reading.** Each format is read into text along with the exact place each piece came from: a cell in a
table, a range of bytes in a document, a region of an image. Text found inside a picture joins the same
pass as everything else, so a name in a screenshot can be linked to the same name in an email.

**Who is who.** The default resolver is deterministic: the same input gives the same answer, and it
makes no model calls. It treats two kinds of clue differently. An email address, a phone number or a
username can match exactly. A name cannot, because it comes with spellings, initials and typos.

The rule that matters most is that evidence has a direction. `Jordan Lee <jordan.lee@example.com>` in an
email header ties that name to that address. Two strings that only sit in the same message are tied
weakly, and no amount of weak evidence merges anyone, because recipient lists would chain strangers
together. Things that many people use are identities of their own: a team inbox, or an address that
several people sign for, never becomes a bridge between two people. Anything linked to too many others
does not merge on its own.

For the close calls there is a slower path. It groups likely matches into small blocks, asks a model to
sort each block, and only merges on agreeing votes. It is off by default, because it is slower and costs
money on every run.

**One fake per person.** Every mention of a person takes its fake from that person's one identity, in the
same format and of the same length. An email address still looks like an email address, and a name on a
form still fits its box. The table that pairs each real value with its fake is the key that undoes
everything, so it never leaves with the data.

**Writing it back.** Each fake goes back to the place the reader recorded, never by searching for the
original text. Pictures get no fake: faces, logos, codes and personal text in an image are masked, and
an image the pipeline cannot read is not shipped as it was.

The whole pipeline runs on Temporal across GKE and EKS, and resolution is a Go service that keeps its
memory bounded however much data comes in.

## What it gives up

Strict evidence costs true matches. A person who appears as a first name on one page and a phone number
on another may stay split, and a merge the evidence does not support does not happen. That is the trade
I wanted.

A split leaves one person with two fakes, which reads a little oddly. A merge pins one person's
words and details on someone else, and that cannot be undone once the data has left. So every close call
should split.

The deterministic default gives up the matches that only a careful reader of the context would see. In
return it gives the same answer twice, and every merge can be traced to the evidence behind it. It also
adds no model bill to a run.

Writing back by position is harder to build than search, because every step has to carry the locations
along. Search would be simpler, and it would also change every innocent copy of the same string.

## Results

With the eval suite I built alongside the resolver, accuracy on a labeled set went from 85% to 95%. That
says the resolver is right more often. It does not say which way the remaining mistakes lean, split or
merge, and that is what decides whether anyone gets hurt.

Every change to the resolver now shows its score against the main branch, next to the spread between two
runs of the same build. A change smaller than that spread is not a finding.

## What I took from it

Decide which mistake you can live with before you write any code. Every threshold after that is the same
decision made again in small.

And do not trust a clustering score on its own. Put every mention in one cluster and you have found every
true match. Put every mention alone and you have made no wrong merge. A useful score makes both of those
answers look bad, and I want to see splits and merges side by side.
