When a business-intelligence team at Coca-Cola needed supply-chain data, they filed a request and waited for someone to pull it. Over three co-op terms I worked on making that wait go away, for data and for documents.

The scale was the problem. There were more than 300 global supply-chain datasets behind those requests, and the ETL run took 9 hours.

## The API

People were the interface: every request was handled by hand. I designed the [CPS Analytics API](https://confused-locket-f0c.notion.site/CPS-Advanced-Analytics-API-5618147fdf0f4056abac5acb5dce3222), Django REST endpoints to create, read, update and delete records across the 300+ datasets, so business-intelligence teams could run their own operational queries.

## The chatbot

Documents had the same problem as data. I built an internal assistant in Haystack so employees could ask the internal knowledge bases questions in plain language instead of hunting through them.

<figure class="os-figure">

```text
 a question in plain words
            |
            v
 BM25 keyword search over Elasticsearch
            |   a short list of candidate passages
            v
 RoBERTa reader: picks the answer out of them
            |
            v
 the answer
```

<figcaption>The chatbot's two stages: a fast keyword search narrows the knowledge bases to a few passages, then a reading model picks the answer from those passages.</figcaption>
</figure>

This design has limits. Keyword search misses a passage that uses different words from the question, and a reader like this can only answer with words that are already in a document.

## The pipelines

I rebuilt a Python data-access library and the monitoring platform around it. Support tickets fell by 63%, and the ETL runtime went from 9 hours to 6.5. I also built Azure Data Factory pipelines that process 300+ datasets daily with PySpark and SQL on Databricks, cut the transformation step’s runtime by 60%, and added CI/CD with automated data validation.
